## 1. XE-0199 - FIXED

- Title: desk account-link flow merges a victim reporter account (sealed reports + payout) into whoever requested the link. Assessed High, award 2,000 XE, patch_refs 1 (desk commit `1fac5b2`).
- Claimed defect: `desk/api/reporter.py:254` `_email_link` stored `link_to` from the initiator session; `email_finish` honoured it verbatim for whoever clicked; `desk/services/reporters.py:170-202` `from_email`/`merge` moved all tickets, identities and payout to the survivor. Same sink in GitHub, Discord and XE-key resolvers.
- Fix in commit `1fac5b2` (2026-11-04, "Close the desk's own bounty findings: identity, disclosure, log and mirror"): new `_link_target(ch, who)` returns `link_to` only if the completing browser is still signed in as that same reporter; `email_finish` now raises 400 ("open this link in the browser where you asked for it, signed in to the same account") unless `who.reporter.id == link.reporter_id`; `_email_link` raises 409 if a signed-in requester names an address already on another account ("never a merge by mail"); `email_start` now runs the CSRF check for signed-in callers; mail copy corrected to say the link only works in the signed-in browser that asked and never moves an existing account. GitHub and Discord callbacks use the same `_link_target`. Still present at desk HEAD `95660df` (`reporter.py:139` `_link_target`, `:328` email_finish guard). Team thread: fix confirmed, assessment High.
- Re-report check: desk search `q=account-link` (3 hits) and `q=merge reporter` (0 hits) show no re-report of the takeover. Nearest is XE-7720 (new, Note, 2026-11-11): a legitimate merge silently drops the merged-away row's second email/GitHub/platform identity, explicitly distinguishing XE-0199 ("no award is diverted and no account is taken over") and asking for refuse-or-warn, not a takeover. XE-11623 (email enumeration oracle on the pre-auth link flow) is a different limb. Neither is this defect.
- Settling evidence if still doubted: run a local desk at `1fac5b2` and repeat the original PoC steps D0-D6 with two throwaway reporter accounts; the victim click must now 400 instead of issuing an attacker session. A live test would need a real victim click and is out of scope here.

## 2. XE-0789 - FIXED (original); Discord bypass variant already filed as XE-1799

- Title: kind conversion rewrites a paid ticket's status and re-queues its award. Claimed High, assessed Medium, award 200 XE, patch_refs 1 (desk commit `fb93a8a`).
- Claimed defect: `desk/api/team.py:117-141` `set_kind` converted bounty to support with `set_status(..., "triaging", force=True)`, skipping the TRANSITIONS check, so a paid ticket demoted to triaging and re-walked to awarded; `desk/services/reporters.py:426-436` `payout_rows` selected on status awarded alone and never read `paid_ref`.
- Fix in commit `fb93a8a` (2026-11-08, "Desk findings: auth, identity, payouts, status, log and intake fixes"): `set_kind` now computes `settled = ("accepted", "fixing", "patched", "disclosed", "awarded", "paid")` and 409s if `t.award_xe or t.award_approved_at or t.status in settled` ("no kind conversion past accepted, no walk-back from awarded or paid"); `payout_rows` now filters `Ticket.paid_ref == ""`; a new treasurer-only `POST /v1/team/tickets/{id}/paid {paid_ref}` route (`mark_paid`) records payment. Commit message names XE-0789 explicitly. Still present at desk HEAD `95660df` (`team.py:125-126` settled guard, `reporters.py:641` paid_ref filter). Team thread: "The fix is on the desk now; this ticket moves to patched."
- Re-report check: desk search `q=kind conversion` (8 hits) shows XE-7054 (new, Medium, 2026-11-11): conversion publishes the held assessment to anonymous readers because `set_kind` clears only claim fields and `assessment_held` keys off kind. Different field family, and its author explicitly distinguishes XE-0789 ("fixed by the settled-status guard, which does not block this"). XE-1799 (triaging, Minor) is the direct bypass variant: `set_award` accepts awards on non-bounty tickets and Discord `/bounty` converts them via `convert_to_bounty`, which has no award/status check, bypassing the XE-0789 guard the web route enforces. That is exactly the remaining bypass in this family and it is already filed. Do not re-file it.
- Residual, not fileable: XE-7054 (assessment leak on conversion) is a distinct live claim already filed by another reporter.

## 4. XE-0956 - FIXED (hardening; team says the disclosure path was not reachable)

- Title: agent-proposed reply drafts are evaluated with str.format(), server memory disclosure up to the log signing seed. Claimed Severe, assessed Minor, award 25 XE, patch_refs 1 (desk commit `fb93a8a`).
- Claimed defect: `desk/services/proposals.py:109-114` adoption filled a `reply_draft` with `thread.fill(ctx, str(value), t)`; `desk/services/thread.py:193-212` `fill` returned `tpl.format(**values)`, whose mini-language permits attribute traversal; `ticket_url` is a function in a module importing `Context`, whose module global `_ctx` holds `settings` (SMTP password, GitHub OAuth secret) and `signer` (ed25519 log seed); the evaluated draft was stored and readable back by the same agent token.
- Fix in commit `fb93a8a`: `fill` no longer calls `tpl.format`; it calls new `_fill_known(tpl, values)`, which substitutes only `{name}` placeholders the desk knows by plain substitution ("no attribute or index access, no format specs, so a draft cannot reach into the ticket or the config (XE-0956)"). Commit message: "fill never names a held tier and only fills known placeholders (XE-0733/0956)". Still present at desk HEAD `95660df` (`thread.py:345` `_fill_known`, `:351` definition, no `tpl.format` in `fill`). Team thread: "the values it substitutes are all plain strings, so the memory-disclosure path described is not reachable, but the use of format on agent text is a hardening item we are taking" and "The fix is on the desk now."
- Re-report check: desk search `q=str.format reply_draft` (0 hits) and `q=XE-0956` (3 hits) show no re-report of the format path. Nearest is XE-7202 (new, Minor): regression of XE-0426, `Ticket.draft` is never sealed, team reply-drafts on private tickets sit plaintext at rest because `seal_thread` misses the draft on a public-to-private flip. Different mechanism (sealing at rest, not format evaluation) and already filed.
- Verdict note: assessed Minor, not Severe, because the team judged the traversal unreachable in practice. A re-report would need to prove a non-string value actually reaches `fill` at HEAD; none was found in this pass, and `_fill_known` removes the primitive entirely.

## 5. XE-0959 - FIXED

- Title: DAO harness public reads hold a pooled DB session across node fan-out, about 20 concurrent requests pin the whole app. Claimed High, assessed Minor, award 250 XE, patch_refs 1 (dao commit `dao@704238b`).
- Claimed defect: dao `ui.py:234-252` (/records), `256-273` (/members) and `api/public.py` legal identifier/registry/keyset routes held a 20-connection pool session open across up to 6 sequential node round-trips; slow node responses pinned all slots; the existing NODE_READ guard was not applied to these routes.
- Fix in dao commit `704238b` (2026-11-07, "One guard for payload strings and driver errors..."): commit message states "Public node reads are shared for ten seconds and every route that makes one is under NODE_READ (XE-0959)". Diff: `dao/ui.py` and `dao/api/public.py` import `NODE_READ, enforce_ip` and call `enforce_ip(request, NODE_READ)` on the public read routes. At dao HEAD `74b5f6e`, `/records` and `/members` still open `async with session() as db:` for DB reads only and the node calls (`records.public_keyset`, `onchain_registry`, `treasury`) run after the session block closes, so no pool slot is held across the fan-out; `api/public.py:296-312` documents the long-lived stream takes no request-scoped session. Team verdict valid, assessed Minor.
- Re-report check: desk search `q=DAO pool session` (0 hits) and `q=XE-0959` (1 hit) show no re-report of the DAO pool. Nearest is XE-9077 (new, Minor): desk `/v1/events/stream` pins one pooled DB connection per authenticated stream, 20 streams stall the desk. Different app (desk, not DAO harness), different endpoint, already filed.
- Caveat: fix verified in dao source, not by a live DAO deployment load test. A live re-test would need the deployed harness URL and 20 concurrent slow reads; the code evidence (session closed before node calls plus NODE_READ) closes the claimed mechanism.

## 6. XE-1127 - FIXED (design gap; team said most cited code did not match the repo)

- Title: dao/services/portal.py portal.decide sets terminal decided status on interim defer/refer_to_resolution dispositions and rejects open resolutions in _decision_resolution. - Claimed defect: `dao/services/portal.py:130-156` `decide()` set `p.status = "decided"` for every disposition including interim `defer` and `refer_to_resolution`, and `138` only allowed decisions on `passed` proposals, so a deferred proposal could never later be adopted or declined; `_decision_resolution()` (`159-169`) demanded `r.status == "signed"`, rejecting active `open` resolutions.
- Fix in dao commit `704238b`: `decide()` now defines `FINAL = ("adopt", "decline")` and, when `pr.status == "decided"`, allows a further decision only if the recorded decision was interim and the new one is final ("`defer` and `refer_to_resolution` say 'not yet': each may be followed by one final adopt or decline, with the earlier record kept under `history` (XE-1127)"); `_decision_resolution` is called with `passed=decision != "refer_to_resolution"`, so a referral accepts an `open` resolution while an adopt still needs a passed one. Still present at dao HEAD `74b5f6e` (`portal.py:40` FINAL, `:526-528` interim comment, `:541` passed flag). Team thread: "Most of the cited code (statuses, permission split, line numbers) does not match the repository; the one point that holds is that a deferred proposal cannot later be adopted or declined, which we are treating as a design gap and reviewing."
- Re-report check: desk search `q=portal decide defer` (0 hits) and `q=XE-1127` (1 hit) show no re-report. Nearest is XE-14652 (new, Minor): live tally reports `unsettled_rows=0` for a vote held out as unsettled, a tally computation issue, not the decide state machine.
- Verdict note: the fix addresses the one point the team accepted. The permission-split half of the claim (an operational_review officer unilaterally deferring) was not confirmed by the team and is not a fileable re-report on this evidence.

## 7. XE-1448 - FIXED (original repro); incomplete-guard variants already filed by others

- Title: payout address field incorrectly accepts public addresses as private key seeds, unexpected key derivation. Claimed High, assessed Medium, award 125 XE, patch_refs 1 (desk PR `8b371c5`).
- Claimed defect: an XE address and a key seed share the same format (64 hex); pasting a public address into the payout address field derived a new key pair from that public string and bound the derived address, so a payout could go to an address the user does not control.
- Fix: team thread on the ticket confirms "the change that refuses an address pasted as a seed and shows the derived address before binding is live". At desk HEAD `95660df`, `desk/services/reporters.py:363` `bind_payout` raises 400 if `address in await _public_as_seed(db, r)` ("that key was made from a public address used as a seed, so anyone who knows the address could spend from it"), and `_public_as_seed` (`:396-409`) derives keys from the reporter's own public strings (login addresses, current payout address, addresses on their own tickets). The original repro (own address as seed) is therefore blocked.
- Re-report check: the guard is narrow, and every variant of that narrowness is already filed, all still new and unassessed: XE-11915 (new, High, 2026-11-13) "Payout bind accepts a foreign public address as seed, award spendable by anyone who knows the address" (guard checks only the reporter's own strings); XE-6374 (new, Minor) same foreign-address variant; XE-6046 (new, Medium, 2026-11-11) "Desk XE login accepts a public address as a seed, the XE-1448 guard covers payout only" (login/add-key path has no guard, proven on a local desk copy); XE-6376 (new, Minor) "Desk payout bind accepts the all-zero seed (and any trivial seed), no server-side weak-key check". Filing any of these again would duplicate an open ticket. Do not file.
- Settling evidence if still doubted: bind payout on a local desk at HEAD with the reporter's own public address as seed; it must 400. A live test would bind a payout address on a real reporter account and is out of scope here.

## 8. XE-1479 - FIXED

- Title: dao/config.py and dao/services/portal.py Config.excluded_accounts() forces agent seat voting weight to zero and omits signer-backed dao/fee accounts. Claimed High, assessed Minor, award 100 XE, patch_refs 1 (dao commit `55ee9d4`).
- Claimed defect: `dao/config.py:175-200` `excluded_accounts()` merged `self.agent_accounts` into `excluded_accounts` whenever `participating_wallet.exclude_agent_accounts` was true, so `portal.vote()` set every agent seat weight to 0 and the 100 XE stipend and 1% `max_weight_share` cap were unreachable; it also read dao/fee addresses only from `config/schedule_c.yaml` (empty there, signer authoritative) and never consulted `ctx.signer`, so the live fee escrow and dao accounts were omitted from exclusion.
- Fix in dao commit `55ee9d4` (2026-11-08, "Close thirteen desk reports: accounts, tally share..."): commit message states "Fixes xe#1479: the company's accounts (dao, fee) come from the signer when Schedule C leaves them blank, and agent seats are no longer in excluded_accounts; their weight is bounded by the cap." Diff: `config.py` adds `signer_accounts` (name to address, from the loaded keyfile) and `accounts()` merges signer addresses; `excluded_accounts()` docstring now says "Agent seats are not here: their weight is bounded by `agents.max_weight_share` in the tally and their participation by `exclude_agent_accounts`; zeroing them would make both dead (XE-1479)", and the `ex |= self.agent_accounts` line is removed; `portal.py` vote/tally now go through `eligibility()`, which checks `exclude_agent_accounts` only for participation. Still present at dao HEAD `74b5f6e` (`config.py:208-212` docstring and set, `portal.py` eligibility path). Team thread: behaviour confirmed, "it is being handled".
- Re-report check: desk search `q=excluded_accounts agent` (0 hits) and `q=XE-1479` (2 hits, both unrelated) show no re-report. Nearest hits are XE-14929 (near-duplicate phrases) and XE-15688 (operation-binding attestations), neither is this defect.
- Caveat: fix verified in dao source, not by a live DAO vote. A live re-test would need a designated agent seat voting on a live proposal; the code evidence (removal of the union plus signer-backed accounts) closes both claimed limbs.
